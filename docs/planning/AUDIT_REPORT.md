# Auditoría técnica del repositorio

**Línea base:** `61e08eae0b7674d9046050ee8313457fc60fa27c` en `main`. Revisión 17 de noviembre de 2026. Se revisaron los 29 archivos versionados, los metadatos de historial relacionados con datos generados y las entradas de CLI. Se excluyeron los contenidos de `config/.env`, logs y cachés locales. No se envió tráfico de auditoría a objetivos ni solicitudes al proveedor de IA.

## Inventario y rutas de ejecución

| Área | Archivos y responsabilidad observada |
|---|---|
| Entradas | `main.py` carga dotenv desde CWD y monta dos grupos Typer. `migrate.py` llama `create_all`. `cli/audit.py` orquesta proveedores, red, JSON y DB desde la CLI. `cli/report.py` lee JSON, llama al LLM y genera HTML. |
| Aplicación y dominio | `application/audit_service.py` encadena cuatro funciones síncronas. `domain/models.py` aporta un enum y un dataclass de hallazgo. |
| Verificaciones | `core/recon.py` realiza GET, registra cabeceras y busca ausencias. `core/scanner.py` intenta conexiones TCP secuenciales. `core/xss.py` y `core/sqli.py` añaden parámetros fijos y examinan respuestas. `core/settings.py` mezcla YAML y valores por defecto. `config/config.yaml` define puertos, timeout, payloads y modelo. |
| IA | `gpt/client.py` encapsula Groq y un cliente global. `gpt/prompts.py` compone textos. `gpt/summarize.py` pide Markdown. |
| Persistencia | `infra/db.py` configura SQLite local. `infra/models.py` declara una tabla. `infra/repository.py` inserta y confirma hallazgos. |
| Exportación | `reports/report_html.py` renderiza HTML de uso efectivo. No se encontró llamador de `core/report.py`, que guarda JSON fechado. `core/logger.py` configura logging y archivo local al importarse. No se encontró importador de este logger. |
| Fabricación y calidad | `requirements.txt` declara 7 dependencias con mínimos abiertos. `.github/workflows/python-app.yml` instala y prueba con Python 3.10 y aplica flake8 con bloqueos parciales. `tests/test_payloads.py`, `tests/test_recon.py`, `tests/test_xss.py` contienen 4 pruebas. |
| Distribución | `README.md` documenta Groq, migración y CLI con URL de clonación de ejemplo y un objetivo público. `LICENSE` establece MIT. `.gitignore` contiene exclusiones duplicadas de evidencia y oculta altas bajo `reports/` aunque su renderer ya está versionado. No hay empaquetado, Docker, frontend ni servidor API. |

`audit run` valida estructura → inicializa Groq → GET de reconocimiento → TCP → XSS → SQLi → escribe JSON por dominio → inserta hallazgos en SQLite. `report generate` confía en JSON importado → construye prompt → pide Markdown → lo convierte en HTML. El GET de reconocimiento toca el servicio, por lo que es reconocimiento activo de bajo impacto. El dominio puro y la separación inicial de IO son aprovechables. La aplicación importa adaptadores concretos y no tiene puertos ni invariantes de negocio. La ubicación por carpetas aporta estratificación inicial, sin un modelo DDD operativo ni inversión suficiente de dependencias.

## Comprobaciones

- `python main.py audit --help` y `python main.py report --help` exponen `run` y `generate`.
- Python 3.13.14 y pytest 9.1.1. Pasaron cuatro pruebas con `requests.sessions.Session.request` simulado en error de conexión, resolución y sockets bloqueados para el proceso de pruebas y `GROQ_API_KEY` retirado del entorno de ese proceso. La prueba XSS verifica tipo de retorno y permite una lista vacía. Las pruebas no cubren un HTTP real, alcance, redirects, falsos positivos ni cancelación.
- Las comprobaciones de aceptación de URL y de HTML reemplazaron respectivamente audit/cliente e IO. El análisis de destinos y redirecciones restantes es estático.
- La madurez actual es **prototipo CLI de auditoría web**. El flujo es demostrable con fixtures y contiene piezas reutilizables. El control previo a la red, la trazabilidad y el aislamiento determinan la transición a un entorno empresarial.

## Registro de línea base de TASK-001

- **Dependencias directas.** Mínimos declarados en `requirements.txt`: Typer 0.12, Requests 2.31, PyYAML 6.0, Groq 1.7, httpx 0.27, python-dotenv 1.0 y SQLAlchemy 2.0. El entorno de verificación local con Python 3.13.14 usó respectivamente 0.27.2, 2.34.2, 6.0.3, 1.7.0, 0.28.1, 1.2.2 y 2.0.52. Herramientas de verificación: pytest 9.1.1 y flake8 7.3.0. Este registro es una instantánea local, el lock reproducible queda en TASK-010.
- **Revisión de historial.** Se agruparon rutas únicas de `git log --all --name-only` por ubicación y extensión. Aparecen 3 HTML y 3 JSON bajo `results/`, 5 PDF y 1 JSON bajo `reports/`, y 1 base SQLite. Bajo `reports/` también hay rutas de código Python, excluidas del conteo de evidencia. La revisión se limitó a metadatos. No verificó contenido sensible, accesos previos ni copias externas.
- **Verificación del índice.** El CI comprueba que las rutas versionadas no coincidan con patrones de exclusión, sin imprimir sus nombres al detectar infracciones. `git check-ignore` confirmó exclusión para ejemplos de resultados, informes generados, evidencias, capturas, archivos de entorno, base local y log. El renderizador y `.env.example` se pueden versionar. El historial de artefactos se conserva.
- **Pruebas herméticas.** `python -m pytest` instala el bloqueo de DNS y conexiones Python antes de la colección. Las pruebas usan respuestas HTTP, sockets y respuestas de Groq simulados. La clave del entorno se enmascara durante la suite. Cada fixture comprueba el resultado del caso probado y el bloqueo falla si una prueba intenta abrir red real.
